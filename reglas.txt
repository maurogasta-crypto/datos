rules_version = '2';

// ═══════════════════════════════════════════════════════════════
//  PANEL DE DATOS — reglas de Firestore del proyecto datos-830f8
//  v5 · 2026-09-14 · entra `lineas/`: en qué se está trabajando y quién
//  v4 · 2026-09-13 · la bóveda se define por PROPÓSITO, y `fichas/` sale
//
//  ⚠ ESTE ARCHIVO ES UNA COPIA. La autoridad es lo que está publicado en
//  la consola de Firebase. Una copia en el repositorio se desactualiza en
//  silencio, así que el panel trae una prueba —«La puerta» → Probar— que
//  intenta leer una colección que estas reglas no declaran: tiene que
//  FALLAR. Esa negativa es lo único que demuestra que lo publicado es esto.
//
// --8<-- PLANTILLA
//  ⚠ ESTE ARCHIVO ES LA PLANTILLA, Y NO SE PEGA TAL CUAL. Los dos UID de acá
//  abajo dicen TU-UID-ACA y UID-DEL-AGENTE a propósito: este repositorio es
//  público y un UID real no entra nunca. La versión que SÍ se pega la arma el
//  panel —solapa «La puerta»—, que baja ESTE MISMO archivo, reemplaza este
//  párrafo por el que corresponde y pone los UID adentro. Esa versión existe
//  en pantalla y en ningún otro lado: ni en un archivo, ni en un chat.
//
//  Y por eso el texto vive una sola vez. Hasta `panel-14` el panel traía las
//  reglas escritas de nuevo, a mano, adentro de `index.html`: dos copias del
//  mismo texto que había que acordarse de tocar juntas, que es exactamente
//  el error que este ecosistema ya cometió cuatro veces con los sellos. Si
//  acá cambia una línea, cambia sola la que el panel ofrece copiar. No queda
//  nada que sincronizar.
//
//  Los dos marcadores `--8<--` de arriba y de abajo los usa el panel para
//  encontrar este párrafo. Se pueden borrar: si no están, el texto sale
//  igual, con este párrafo adentro y todo. Nada se rompe.
// --8<-- FIN PLANTILLA
//
//  ⚠ LAS REGLAS SE SUMAN: basta con que UN bloque permita para que el
//  acceso quede abierto. Por eso esto se pega SIEMPRE completo, nunca por
//  fragmentos.
// ═══════════════════════════════════════════════════════════════
//
//  QUÉ CAMBIÓ EN LA v4, Y POR QUÉ NO ES VOLVER ATRÁS.
//
//  La v4 le devuelve `fichas/` al equipo. Leído rápido parece desandar la v3,
//  y no lo es: lo que cambió es el CRITERIO con el que se decide qué va en la
//  bóveda, y ése es el que estaba mal desde el principio.
//
//  La v3 la definió por el RIESGO: «la colección donde una credencial PUEDE
//  aparecer». Suena prudente y es inaplicable — con ese criterio cualquier
//  colección termina sellada, porque en cualquiera PUEDE caer una contraseña.
//  Mauro lo dijo mejor que nadie el 2026-09-13: no encontraba claridad sobre
//  qué poner en una ficha. No la había.
//
//  La v4 la define por PROPÓSITO, y la pregunta se contesta sin pensar:
//
//      ¿abre algo?  →  `claves/`, sellada, de Mauro y de nadie más.
//      ¿no abre?    →  `fichas/`, del equipo.
//
//  Lo que se gana no es comodidad: es que ahora hay un criterio que se puede
//  aplicar. Un sello que nadie sabe cuándo aplicar no protege nada, y además
//  dejó las fichas sin mantener nueve días.
//
//  ⚠ LO QUE NO SE SALTEA. Publicar la v4 con la contraseña del 2026-09-11
//  todavía adentro de una ficha significa que un agente la leyó. Es el
//  pendiente `panel:R4`: primero se mueve a `claves/`, después se publica.
// ═══════════════════════════════════════════════════════════════
//
//  QUÉ CAMBIÓ EN LA v3, QUE LA v4 CORRIGE.
//
//  La v2, del 2026-09-11 a la mañana, le dio acceso al agente a todo menos
//  `claves/`, y decía de `fichas/`: «NO van contraseñas acá — para eso está
//  `claves/`». Esa frase era un deseo, no una regla.
//
//  La primera verificación del acceso, esa misma tarde, encontró adentro de
//  una ficha un usuario y una contraseña reales de un servicio. Las reglas
//  hicieron exactamente lo que decían hacer. El dato estaba en el lugar
//  equivocado, y ninguna regla puede adivinar que un campo llamado `valor`
//  es una contraseña.
//
//  Así que `fichas/` pasó a la bóveda, con este criterio: es la colección
//  donde una credencial PUEDE aparecer. El sello es por lugar, no por
//  contenido — eso sigue siendo cierto y es lo que la v4 conserva.
//
//  Lo que se escribió entonces: «lo que se pierde es que el agente ya no
//  mantiene las fichas solo; lo que se gana es que no hay ninguna colección
//  abierta donde una contraseña pueda caer por descuido. Vale la pena.»
//
//  A los nueve días se vio que no valía la pena, y por un motivo que no se
//  había previsto: **lo que se perdió no era una comodidad del agente, era el
//  mantenimiento.** Nadie mantuvo las fichas. Y el criterio «donde PUEDE
//  aparecer» nunca le dijo a Mauro qué poner adentro. La v4 lo reemplaza.
// ═══════════════════════════════════════════════════════════════
//
//  EL MODELO, EN DOS LÍNEAS.
//
//    · MAURO  — todo, sin excepción.
//    · AGENTE — todo MENOS lo que abre algo. O sea: todo menos `claves/`.
//
//  LO QUE HACE QUE ESTO SEA SEGURO, y es la parte que no se toca:
//
//  1. El agente entra con un usuario COMÚN de Authentication, así que todo
//     lo que hace pasa por estas reglas. NO se usa una cuenta de servicio:
//     ésa saltearía las reglas por completo y la bóveda dejaría de estar
//     sellada. Es la diferencia entre una puerta cerrada y no tener puerta.
//  2. `claves/` le está negada de lectura Y de escritura. No es que le cueste
//     leerla: la base le dice que no. Es UNA colección, y esa línea no se
//     negocia nunca.
//  3. La contraseña del propio agente vive en las variables de entorno del
//     entorno de Claude Code. No está en ningún repositorio ni en ningún chat.
//  4. Lo mismo está escrito en `selladas` del proyecto `panel` en
//     `datos/herramientas/firestore.mjs`, que corta antes de salir a la red.
//     Ese archivo da el mensaje claro; esta regla da la garantía. Si cambia
//     uno, cambia el otro en la misma tanda.
// ═══════════════════════════════════════════════════════════════

service cloud.firestore {
  match /databases/{database}/documents {

    function soyYo() {
      return request.auth != null && request.auth.uid == 'TU-UID-ACA';
    }

    function esAgente() {
      return request.auth != null && request.auth.uid == 'UID-DEL-AGENTE';
    }

    function equipo() {
      return soyYo() || esAgente();
    }

    // ── EN QUÉ SE ESTÁ TRABAJANDO, Y QUIÉN ──
    //
    // `lineas/` entra con la v5 (2026-09-14). Es la única colección que
    // existe para que dos CHATS no se pisen: una línea de trabajo se «toma»
    // antes de tocar código, y quien la tomó queda escrito adentro. Sin esto,
    // dos sesiones abiertas en paralelo descubren que hicieron lo mismo —o lo
    // contrario— recién cuando una pisa a la otra.
    //
    // Va al equipo, y tiene que ser así: el que necesita leerla al abrir y
    // escribirla al cerrar es justamente el agente. No es sensible — son
    // títulos de trabajo, no datos de nadie.
    match /lineas/{id}     { allow read, write: if equipo(); }

    // ── El estado de los proyectos y el reglamento ──
    // No es sensible. Lo genera el agente y también lo escribe: es lo que
    // saca de encima el toque de Mauro por tanda.
    match /proyectos/{id}  { allow read, write: if equipo(); }
    match /pendientes/{id} { allow read, write: if equipo(); }
    match /tandas/{id}     { allow read, write: if equipo(); }
    match /protocolos/{id} { allow read, write: if equipo(); }

    // ── LA BÓVEDA, QUE AHORA ES UNA SOLA COLECCIÓN ──
    //
    // `claves` es lo que ABRE algo: contraseñas, códigos de recuperación,
    // segundos factores. Sólo Mauro, y sólo desde el panel. Es LA línea del
    // archivo que no se negocia, y si un día un agente pide que se le abra:
    // la respuesta es no, y la cabecera es el motivo.
    match /claves/{id}     { allow read, write: if soyYo(); }

    // ── FICHAS AL EQUIPO: `fichas` la administra el agente, desde la v4 ──
    //
    // Esa línea de arriba la busca el panel —por la frase «FICHAS AL EQUIPO»—
    // para avisar, al lado del botón de copiar, que estas reglas le dan las
    // fichas al agente. Se busca una FRASE y no la línea de la regla a
    // propósito: `index.html` no puede contener una línea de reglas, o sería la
    // segunda copia del texto que todo este diseño existe para que no haya. Y
    // tampoco usa los marcadores de tijera de la cabecera, que el panel BORRA al
    // armar el texto y que en la consola no significarían nada. El banco
    // verifica las dos cosas, y de hecho cazó los dos errores en el primer
    // armado: primero la línea de reglas, después el marcador.
    //
    // Pedido de Mauro el 2026-09-13: «quiero que las fichas las administres
    // tú». Y tenía razón en el fondo: al sellarlas, la v3 se quedó sin nadie
    // que las mantuviera, y eso era justo para lo que existían.
    //
    // LO QUE CAMBIÓ NO ES LA CONFIANZA, ES LA DEFINICIÓN. La v3 definió la
    // bóveda por el RIESGO —«la colección donde una credencial PUEDE
    // aparecer»—, y una categoría definida por lo que podría salir mal no le
    // dice a nadie qué poner adentro. Por eso Mauro no encontraba claridad: no
    // la había. La v4 la define por PROPÓSITO:
    //
    //     ¿abre algo?  →  `claves`, sellada, de Mauro y de nadie más.
    //     ¿no abre?    →  `fichas`, del equipo, la administra Claude.
    //
    // Así la pregunta «¿dónde va esto?» se contesta sola, que es lo único que
    // de verdad evita que una contraseña caiga en el lugar equivocado. El sello
    // sigue siendo por LUGAR — lo que cambió es que el lugar ahora tiene un
    // criterio que se puede aplicar sin pensar.
    //
    // ⚠ ANTES DE PUBLICAR ESTO HAY UN PASO QUE NO SE SALTEA. El 2026-09-11 la
    // primera verificación del acceso encontró un usuario y una contraseña
    // REALES adentro de una ficha — es el pendiente `panel:R4`. Si estas reglas
    // se publican con esa contraseña todavía ahí, la leyó un agente y hay que
    // rotarla. El orden es: PRIMERO se mueve a `claves`, DESPUÉS se publica.
    match /fichas/{id}     { allow read, write: if equipo(); }

    // ── El cierre, que NO cierra ──
    // Ojo con leerlo como un candado: en Firestore los permisos se SUMAN y
    // un `if false` no le resta nada a lo de arriba. Lo que niega de verdad
    // es el deny por defecto — una colección sin bloque propio es
    // inaccesible aunque esta línea no existiera. Se deja escrita como
    // recordatorio de que una colección nueva se agrega a propósito.
    match /{document=**} { allow read, write: if false; }
  }
}
